# План миграции на общий прокси

Три проекта (сайт, байкфит-портал, intervals MCP) на одном сервере, три
репозитория, три сессии Клода. Задача — деплоить их независимо друг от друга.

Документ рассчитан на то, чтобы его прочитала каждая из трёх сессий. Когда
появится репозиторий `infra`, файл переезжает туда — сейчас он лежит здесь
просто потому, что это единственный из трёх репозиториев, который уже есть.

---

### 0.4. Деплой сайта

`.github/workflows/deploy.yml`, триггер — пуш в `main`. Сначала lint (`tsc
--noEmit`), затем по SSH:

```bash
cd /opt/vskiba && git pull && docker compose up -d --build && docker image prune -f
```

Секреты: `SSH_HOST`, `SSH_USER`, `SSH_PRIVATE_KEY`. Есть второй workflow —
ночной бэкап базы через `docker exec` в 03:00 UTC.

Два следствия:

- **`/opt/vskiba` под git.** Правка конфигов руками на сервере либо будет затёрта
  `git pull`, либо уронит деплой конфликтом. Всё идёт через репозиторий.
- **Чужие compose-проекты деплой не трогает.** `up -d` без `--remove-orphans`
  работает только внутри проекта `vskiba`, а `image prune -f` удаляет лишь
  висячие образы. Поэтому MCP и байкфит безопасно жить отдельными проектами.

## 0.5. Что делает nginx сайта — и что обязано пережить перенос

Это чек-лист Фазы 1. Каждый пункт — поведение, которое сейчас работает и которое
легко потерять при переносе в Traefik.

| Поведение | Сейчас | Замена в Traefik |
|---|---|---|
| HTTP → HTTPS | `server :80` → 301 | редирект на entrypoint `web` |
| `www` → апекс **по HTTP** | 301 на `https://doc-skibavv.ru` | middleware redirectregex |
| `www` **по HTTPS** обслуживается как есть | `server_name` включает `www`, редиректа нет | роутер матчит оба имени |
| `/api/` → backend:8000 | `location /api/` | роутер `site-api`, priority 100 |
| `/` → frontend:3000 | `location /` | роутер `site-web`, priority 1 |
| WebSocket для Next.js | `Upgrade` / `Connection: upgrade` | Traefik проксирует ws сам |
| Лимит тела запроса | `client_max_body_size 1m` | `buffering.maxRequestBodyBytes` |
| Таймаут backend | `proxy_read_timeout 30s` | `forwardingTimeouts` |
| `X-Frame-Options: DENY` | `add_header ... always` | middleware headers |
| `X-Content-Type-Options: nosniff` | `add_header ... always` | middleware headers |
| `Referrer-Policy: strict-origin-when-cross-origin` | `add_header ... always` | middleware headers |
| `X-Forwarded-For` / `-Proto` | `proxy_set_header` | Traefik ставит сам |

**Про `www` отдельно — здесь асимметрия, которую легко не заметить.**
`http://www.doc-skibavv.ru` редиректится на апекс (`https://doc-skibavv.ru`), а
`https://www.doc-skibavv.ru` отдаёт сайт **под именем www, без редиректа**.
Если при переносе схлопнуть это в «www всегда редиректит на апекс», поведение
изменится — для пользователей незаметно, но это смена канонического URL, и SEO
это заметит. Решение принимать осознанно, а не по умолчанию.

HSTS сейчас **нет**. Traefik его тоже не добавляет сам — если захотите включить,
это отдельное решение (и назад откатывается тяжело из-за кеша браузеров).

## 1. В чём корень проблемы

Сегодня nginx **принадлежит проекту сайта**: объявлен в его `docker-compose.yml`,
конфиг в его репозитории, порты 80/443 держит его контейнер. Всё, что хочет
наружу, вынуждено проходить через чужой репозиторий.

Из этого следуют три неприятности:

- маршруты байкфита и intervals придётся коммитить в репозиторий сайта;
- редеплой сайта перезапускает nginx, то есть кратко роняет все проекты сразу;
- выпуск сертификата для нового домена гасит nginx (`certbot --standalone`),
  и снова ложатся все.

Развязка одна: **прокси не должен принадлежать ни одному из трёх проектов.**

## 2. Принцип: прокси — четвёртый проект

```
infra/            ← новый репозиторий: Traefik, сеть edge, ACME
BusinessCardSite/ ← сайт
bikefit/          ← байкфит-портал
intervalsicugptcoach-public/ ← MCP сервер
```

`infra` владеет портами 80/443 и выпуском сертификатов. Три остальных проекта
**не публикуют портов вообще** и объявляют свою маршрутизацию метками в
собственных compose-файлах. Это и есть независимость: `docker compose up -d`
в своём каталоге — маршрут появился, `down` — исчез, чужие репозитории не
затронуты.

## 3. Контракт между проектами

Три сессии Клода не видят друг друга. Всё, о чём они обязаны договориться,
записано здесь — каждая сессия читает этот раздел перед тем, как что-то менять.

### 3.1. Сети

| Сеть | Кто создаёт | Кто подключается |
|---|---|---|
| `edge` | `infra` | Traefik + только те контейнеры, которым нужен внешний трафик |
| `<project>_internal` | сам проект | БД, воркеры, бэкенды — всё внутреннее |

Правило: **база данных никогда не подключается к `edge`.** Сейчас у сайта всё
свалено в одну плоскую сеть `vskiba_web`, включая postgres — при миграции
разделяется.

В compose проекта `edge` объявляется внешней, чтобы Compose её не создавал и
не удалял:

```yaml
networks:
  edge:
    external: true
```

### 3.2. Точки входа и сертификаты

| Имя | Значение |
|---|---|
| entrypoint `web` | :80, редирект на `websecure` |
| entrypoint `websecure` | :443 |
| certresolver `le` | Let's Encrypt, challenge HTTP-01 |

Проект объявляет `traefik.http.routers.<имя>.tls.certresolver=le` — и всё,
сертификат выпускается и продлевается сам.

### 3.3. Именование роутеров — здесь легко выстрелить себе в ногу

Пространство имён роутеров у Traefik **плоское и общее для всех проектов**.
Два проекта, назвавшие роутер `web`, молча переопределят друг друга — без
ошибки, без предупреждения, просто маршрут одного из них перестанет работать.

Соглашение: `<проект>-<назначение>`.

| Проект | Роутеры |
|---|---|
| сайт | `site-web`, `site-api` |
| байкфит | `bikefit-web` |
| intervals | `icu-mcp` |

То же для сервисов и middleware.

### 3.4. Обязательные правила

- **`--providers.docker.exposedbydefault=false`** в Traefik. Контейнер попадает
  в маршрутизацию, только если явно поставил `traefik.enable=true`. Без этого
  Traefik попробует выставить наружу вообще всё, включая postgres.
- **Никаких `ports:` в проектах.** Только `expose`. Единственный, кто публикует
  порты — Traefik. Это и есть инвариант, который держит TLS в одном месте.
- Каждый публичный контейнер имеет healthcheck.

### 3.5. Таблица доменов

Это единственная вещь, о которой сессии не могут договориться сами.

| Домен / путь | Проект | Роутер | Приоритет |
|---|---|---|---|
| `doc-skibavv.ru/api/` | сайт (backend) | `site-api` | 100 |
| `doc-skibavv.ru/icu/` | intervals MCP | `icu-mcp` | 100 |
| `doc-skibavv.ru`, `www.doc-skibavv.ru` | сайт (frontend) | `site-web` | 1 |
| `bikefit.doc-skibavv.ru` | байкфит | `bikefit-web` | — |

### 3.6. Приоритеты роутеров — обязательно для маршрутов по пути

Три проекта делят домен `doc-skibavv.ru`, и правило сайта `Host(doc-skibavv.ru)`
само по себе совпадает **со всеми** запросами, включая `/icu/` и `/api/`.

По умолчанию Traefik сортирует роутеры по длине правила, и более длинное
`Host(...) && PathPrefix(/icu)` выигрывает у голого `Host(...)`. Полагаться на
это не стоит: длина — неявная величина, она меняется при безобидной правке
правила, и отладка такого «вдруг перестало работать» крайне неприятна.
Приоритет задаётся явно:

```yaml
- traefik.http.routers.icu-mcp.priority=100
- traefik.http.routers.site-web.priority=1
```

Правило: **у проектов, забирающих путь, приоритет заведомо выше**, чем у того,
кто забирает весь домен. Сессия сайта обязана поставить `site-web.priority=1` —
иначе `/icu/` и `/api/` уедут во фронтенд.

### 3.7. Обрезка префикса пути

Приложение MCP обслуживает свои маршруты от корня, поэтому `/icu` снимается
middleware:

```yaml
- traefik.http.middlewares.icu-strip.stripprefix.prefixes=/icu
- traefik.http.routers.icu-mcp.middlewares=icu-strip
```

Так `/icu/<секрет>/mcp` доходит до приложения как `/<секрет>/mcp`.

## 4. Порядок миграции

Строго последовательный. Каждая фаза проверяется до начала следующей.

### Фаза 0 — Traefik рядом с работающим nginx

Traefik поднимается на **временных портах** (8080/8443), nginx продолжает
держать 80/443 и обслуживать сайт. Проверяем, что Traefik видит контейнеры и
маршрутизирует, обращаясь к нему по временному порту.

Риск нулевой: продакшн не затронут, откат — `docker compose down` в `infra`.

### Фаза 1 — переключение сайта (единственный рискованный шаг)

Порядок важен:

1. **Существующие сертификаты подкладываются в Traefik** через file-provider
   (`/etc/letsencrypt` монтируется read-only). TLS начинает работать сразу и не
   зависит от того, успеет ли ACME выпустить сертификат.
2. `docker compose stop nginx` в проекте сайта — порты 80/443 освобождаются.
3. Traefik переводится на 80/443 и перезапускается.
4. Проверка: сайт открывается, `/api/` отвечает, сертификат валиден.

**Откат** (примерно 10 секунд): остановить Traefik, `docker compose up -d nginx`
в проекте сайта. Поэтому сервис nginx **не удаляется** из compose сайта до конца
Фазы 3 — он остаётся как страховка.

**Отдельно про certbot.** Пока Traefik держит порт 80, `certbot --standalone`
выпустить сертификат не сможет: pre-hook остановит nginx, которого там уже нет,
а порт займёт Traefik. Поэтому на шаге 3 `certbot.timer` **выключается**
(`systemctl disable --now certbot.timer`), и удаляется совсем только после того,
как продление через ACME в Traefik подтверждено на практике.

**Про лимиты Let's Encrypt.** Пять одинаковых сертификатов в неделю. Пока
конфигурация обкатывается — использовать staging-CA, иначе можно упереться в
лимит и остаться без сертификата. На боевой CA переключаться, когда всё сходится.

### Фаза 2 — intervals MCP

Первый проект, который подключается «по-новому»: правится только его
собственный репозиторий, `docker compose up -d` — маршрут появился. Ни сайт, ни
`infra` не трогаются.

Это и есть проверка, что независимость действительно работает.

### Фаза 3 — байкфит-портал

По той же схеме. Если Фаза 2 прошла без правок в чужих репозиториях — здесь
сюрпризов не будет.

### Фаза 4 — уборка

Только после того, как всё выше работает:

- удалить сервис nginx и его конфиги из репозитория сайта;
- удалить certbot и его хуки;
- убрать `vskiba_web`.

## 5. Как распределить это по трём сессиям Клода

Главная мысль: **не распараллеливать то, что делит общее состояние.** Docker-хост
один, порты 80/443 одни, и две сессии, одновременно правящие его, — это гонка,
где проигрывает продакшн.

| Фаза | Сессия | Почему так |
|---|---|---|
| 0 и 1 | **одна сессия** (сайт или отдельная infra-сессия) | `infra` и сайт связаны: переключение портов и перенос роутинга сайта — одна атомарная операция. Разносить по сессиям нельзя. |
| 2 | сессия intervals | Правит только свой репозиторий |
| 3 | сессия байкфита | Правит только свой репозиторий |

То есть сессии сайта достаётся вся сложная часть, а двум другим — небольшое
самодостаточное изменение. Это резко снижает объём синхронизации: сессиям 2 и 3
достаточно прочитать раздел 3 и не нужно ничего знать друг о друге.

### Правила, чтобы сессии не мешали друг другу

1. **Раздел 3 — единственный источник истины.** Каждая сессия читает его перед
   работой. Если сессии нужно отступить от контракта — правится контракт, а не
   делается исключение локально.
2. **Одна сессия деплоит в момент времени.** Пока идёт Фаза 1, остальные могут
   готовить изменения и коммитить в ветки, но не выполнять `up -d` на сервере.
3. **Ветки и PR, а не пуш в main.** У сайта пуш в `main` немедленно запускает
   автодеплой. Готовые, но не проверенные изменения должны лежать в ветке.
4. **Порядок мержа = порядок фаз.** Ветка байкфита не мержится раньше, чем
   доказана Фаза 1.

## 6. Найденные проблемы, которые чинятся заодно

Обнаружено при обследовании сервера, к самой миграции отношения не имеет, но
чинить удобно в тот же заход.

### 6.1. PostgreSQL открыт в интернет — критично

`docker-compose.yml` сайта публикует `5432:5432` на `0.0.0.0`. `ufw` выключен,
цепочка `DOCKER-USER` пуста. Проверено снаружи: **порт принимает соединения из
интернета.** Защищает только пароль.

Docker добавляет свои правила в цепочку `DOCKER`, минуя `INPUT`, — поэтому
включение ufw само по себе этот порт не закроет.

**Решение: привязать к localhost.**

```yaml
ports:
  - "127.0.0.1:5432:5432"   # было "5432:5432" — слушало 0.0.0.0
```

Внешний доступ сохраняется, но только через SSH-туннель:

```bash
ssh -N -L 5432:127.0.0.1:5432 root@155.212.185.155
```

После этого клиент вроде DBeaver подключается на `localhost:5432` как обычно,
а из интернета порт закрыт. Ночной бэкап работает через `docker exec` и этой
правки не замечает.

Дополнительно при переходе на схему с сетями (раздел 3.1) postgres уезжает во
внутреннюю сеть проекта и перестаёт быть виден с `edge`.

### 6.2. nginx падает, если апстрим не резолвится

Проверено: при недоступном контейнере `frontend` nginx отказывается стартовать
с `host not found in upstream`. То есть падение одного сервиса мешает подняться
всему прокси. В Traefik этой связи нет — недоступный сервис даёт 502 только на
своём маршруте.

## 7. Принятые решения

| Вопрос | Решение | Следствие |
|---|---|---|
| Где живёт прокси | Отдельный репозиторий `infra` | Нужно создать репозиторий и свой автодеплой для него |
| Адрес intervals MCP | Путь `doc-skibavv.ru/icu/` | DNS не трогаем; обязателен раздел 3.6 про приоритеты |
| Внешний доступ к postgres | Через SSH-туннель | `ports` → `127.0.0.1:5432:5432` |
| Домен байкфита | Поддомен `doc-skibavv.ru` | Нужна A-запись; точное имя уточнить до Фазы 3 |

Остаётся открытым только точное имя поддомена байкфита (`bikefit.` или другое) —
на Фазы 0–2 это не влияет.

### Что нужно сделать вам руками

1. Создать пустой репозиторий `infra` на GitHub.
2. Добавить A-запись для поддомена байкфита → `155.212.185.155` (перед Фазой 3).
3. Решить, кто получает deploy-ключ для `infra` — можно переиспользовать
   существующие секреты `SSH_HOST` / `SSH_USER` / `SSH_PRIVATE_KEY`.

## 8. Проверки — чем именно доказывается каждая фаза

«Работает» означает пройденный список, а не «сайт открылся».

### После Фазы 0

```bash
curl -s -o /dev/null -w "%{http_code}\n" -H "Host: doc-skibavv.ru" http://155.212.185.155:8080/
```

Traefik на временном порту отвечает, продакшн на 80/443 не затронут.

### После Фазы 1 — полный чек-лист

Каждая строка проверяет пункт из таблицы 0.5.

```bash
# HTTP → HTTPS
curl -sI http://doc-skibavv.ru/ | head -2
# www по HTTP → апекс
curl -sI http://www.doc-skibavv.ru/ | grep -i location
# www по HTTPS отдаёт сайт (200, НЕ редирект)
curl -s -o /dev/null -w "%{http_code}\n" https://www.doc-skibavv.ru/
# фронтенд и API
curl -s -o /dev/null -w "front %{http_code}\n" https://doc-skibavv.ru/
curl -s -o /dev/null -w "api   %{http_code}\n" https://doc-skibavv.ru/api/
# заголовки безопасности — должны быть все три
curl -sI https://doc-skibavv.ru/ | grep -iE "x-frame-options|x-content-type-options|referrer-policy"
# сертификат: оба имени и срок
echo | openssl s_client -connect doc-skibavv.ru:443 -servername doc-skibavv.ru 2>/dev/null \
  | openssl x509 -noout -dates -ext subjectAltName
```

Отдельно — WebSocket фронтенда: открыть сайт в браузере и убедиться, что в
консоли нет ошибок подключения ws. Через curl это не проверяется.

### После Фазы 2

```bash
curl -s -o /dev/null -w "%{http_code}\n" https://doc-skibavv.ru/healthz   # 404 — так и надо
curl -s -X POST "https://doc-skibavv.ru/icu/<MCP_SECRET>/mcp" \
  -H "Origin: https://claude.ai" -H "Content-Type: application/json" \
  -H "Accept: application/json, text/event-stream" \
  -d '{"jsonrpc":"2.0","id":1,"method":"tools/list","params":{}}' | head -c 200
```

Плюс обязательно — что **сайт не сломался**: повторить чек-лист Фазы 1. Смысл
Фазы 2 в том, что маршрут добавился без правок в чужих репозиториях; если сайт
при этом пострадал, независимость не достигнута.

### Проверка независимости (после Фазы 3)

Главный тест всей затеи:

```bash
cd /opt/intervals-mcp && docker compose down
```

Сайт и байкфит обязаны продолжать работать, `/icu/` даёт 502 или 404. Затем
`up -d` — маршрут вернулся сам, без reload и без участия других проектов.
